## 一句话总结

指出现有 CR 基准的"完整性鸿沟"——任务碎片化、上下文贫乏、指标狭窄——并发布首个端到端仓库级评审基准：601 例 / 70 个 Python 项目 / 九大问题域，每例携带 issue、PR、commit、仓库状态共 22 个结构化字段，评测框架混合规则校验与模型评审。

## 三重"现实差距"

1. **任务碎片化**：真实评审是"理解问题 → 定位改动 → 形成意见"的整体推理，旧基准把它切成评论生成、代码修订等孤立子任务。
2. **上下文贫乏**：只给小段 diff-hunk，剥掉 PR 描述、关联 issue、仓库结构——模型无法理解变更意图。
3. **评测狭窄**：BLEU 类指标奖励表面文本相似，分不清技术洞察和句式巧合，也验证不了评论位置是否正确。

对比表中 CodeFuse-CR-Bench 是唯一在 Owner/Repo、Base Commit、Issue 陈述、Commit 信息、Review Comment、Merge Commit 等 22 个字段上全部齐备的基准。

## 评测框架

- **规则层**：位置准确性（文件/行/diff hunk 是否命中）+ 语法合法性 + 语义相似度。
- **模型层**：reward model 与 LLM-as-judge 对评论质量、相关性、正确性整体打分。

## 主要发现

- 没有任何单一 LLM 在所有维度占优；Gemini 2.5 Pro 综合最强。
- 不同模型对冗余上下文的鲁棒性差异显著——上下文丰富既是机会也是噪声源。
- 首次给出完整 CR 任务上的 SOTA 基线，后续工作可对照。

## 与本项目的关系

- 06 篇五层评测方案中"仓库级端到端层"的现成底座；601 例规模适中，适合作为 navmap 上下文增强 A/B 实验的载体（同族工具链也让复现成本最低）。
- "上下文丰富但需控制冗余"的发现与本调研"上下文质量 > 模型能力"结论互为印证：喂什么比用什么模型更重要。
- 局限：仅 Python；LLM-as-judge 部分的校准方法未深入（这正是 c-CRAB 用测试裁决补的位）。
