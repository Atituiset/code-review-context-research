## 一句话总结

系统实证回答"在动用复杂索引之前，无索引的 grep 式词法检索能走多远"——答案是：LLM 自主生成 ripgrep 命令的 Naive GrepRAG 就已打平甚至超过图方法（GraphCoder），加上 BM25 重排序 + 结构感知去重后成为新 SOTA。

## 动机：延迟账

在 50 万行以上的仓库，VanillaRAG/GraphCoder 单次检索可超 40 秒（不含建索引时间），而开发者对补全的容忍度是 <0.5s。同场景 ripgrep 只要 1.45s（约 1/35）。静态图/向量索引还会随代码修改迅速失效。

## 方法

**Naive GrepRAG**：LLM 根据光标前上下文生成 ~10 条 ripgrep 命令 → 确定性执行 → Jaccard 相似度重排取 Top-K。

**GrepRAG**（增强版）加两步后处理：
1. **标识符加权重排**：Jaccard 换 BM25，利用 IDF 惩罚 `init`/`config` 这类高频泛化词；
2. **结构感知去重融合**：按行号区间合并重叠/相邻 chunk，重建代码逻辑流。

## 关键发现

- **Naive GrepRAG 全面超过基线**：Python EM 38.61%（RLCoder 36.59%、Vanilla RAG 24.99%），且平均检索延迟 <0.02s。
- **成功归因（RQ2）**：检索关键词分四类——方法名 41.5%、类名 36.0%、变量名 18.4%；23.5% 用通配符模糊匹配；多查询互补聚合。基线失败 64–76% 死在**粗检索阶段**：BM25/Jaccard 的全局词重叠漏掉与补全点弱词汇重叠但语义关键的类定义。
- **失败归因（RQ3）**：GrepRAG 自己的失败 71–75% 是**重排序失败**——关键词歧义噪声 + 上下文碎片化/冗余（两个 grep 命中相邻区域导致重复和"先用后定义"的乱序）；剩余是隐式依赖（继承等结构关系 grep 不到）的根本限制。
- **消融**：只换 BM25 重排仅 +0.51% EM；去重融合才是大头——信息密度瓶颈比排序瓶颈更致命。
- 最终 GrepRAG 在 CrossCodeEval 上相对最强基线 code EM 提升 7.04–15.58%，检索仍 <0.02s。

## 与本项目的关系

- 为 03 篇"零索引 agentic 路线"提供最硬的证据：精确率优先的场景下，显式标识符匹配 > 全局相似度检索；Claude Code 等 agent 内置 Grep 工具的实践被学术验证。
- 同时划清了边界：隐式依赖（继承、宏展开、表驱动分发）是纯词法检索的天花板——这正是需要 navmap 领域图的增量价值所在。
- "先问简单方法能走多远再上重武器"的方法论本身值得写进本调研的评测篇军规。
